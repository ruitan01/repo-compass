RepoCompass

Find your way through unfamiliar code.

Students and junior engineers dropped into an unfamiliar TypeScript/Next.js repository don't know which file to open first. RepoCompass takes a public GitHub URL, suggests where to start reading, and draws the files and their imports as a map to explore.

01 · Problem & users

“Where do I even start?”

A new codebase means hundreds of files and framework rules nobody wrote down. In a Next.js app, what runs first is decided by file names like app/**/page.tsx and middleware.ts, not a main(). How files connect is hidden in imports and path aliases like @/lib/db. Editors help you jump to code you've already found. Nothing gives a newcomer the overview first.

Who it's for: CS students joining a group or open-source project, and junior engineers onboarding onto a TypeScript/Next.js codebase.

03 · Focus: Systems

The hard part is the pipeline

The page is simple. The work is turning a repository into a correct graph within free-tier limits: a data model for files and imports, an external API with rate limits and edge cases, and clear rules for which repos are supported.

v1 runs the whole analysis in one server request, for repos under a size cap. v2 moves it into a background job with live progress, building on what I learned in Assignment 5 (a scheduled worker feeding a Realtime page).

  1. SubmitNext.js appA signed-in user pastes a URL. The server checks it's a supported repo: public, TypeScript/JavaScript, under the size cap.
  2. FetchGitHub APIResolve the branch to a commit, then download the repo once. A commit that's already been analyzed is reused.
  3. ParseRoute handlerRead each file's imports with the TypeScript compiler API, resolving tsconfig aliases.
  4. RankRoute handlerScore entry points from Next.js file conventions, package.json, and how many files import each file.
  5. ShowPostgres → UIFiles and edges are saved, and the page opens the graph with suggested starting points.

Data model (draft)

  • snapshots (repo, commit)
  • files (snapshot, path, kind, entry score)
  • edges (snapshot, from file, to file)
  • analyses (user, snapshot)

Designed failure states

Unsupported repos (private, missing, too large, not TypeScript) and GitHub rate limits each get their own message and next step, not a generic error.

v2: background jobs v2

The same steps move into a queued background job. Supabase Realtime shows each stage as it happens, and larger repos no longer have to finish in one request.

Out of scope

  • Private repositories
  • Languages other than TypeScript/JavaScript
  • Running or building the code
  • Call graphs and type-level analysis
  • Editing code or opening pull requests
  • Very large monorepos (v1 has a size cap)

How I'll know it works

  • v1: graphs for the hand-checked fixture repos match the imports I checked.
  • v1: a signed-in user goes from URL to graph on the live site. Unsupported repos are refused with a clear message.
  • v2: a repo too big for one request finishes as a background job, with each stage shown live.
  • In sessions with at least three people, each finds where a given feature lives in a repo they haven't seen.
  • At the fair, visitors analyze a repo they choose.
